ROS 与 TF：数据流必须有时间和坐标

解释节点、话题、消息、TF 和录包，在运行算法前检查接口。

先修：14 · 位姿与变换链：先看清是“谁到谁”；16 · IMU：从角速度、加速度到运动预测

预计用时：2 次 × 40 分钟。一次学不完就分开，第二天先闭卷重做上一段。

本课新词（4 个）：节点 node / 话题 topic、TF、QoS、ROS 1 / ROS 2。随时可查 术语页。

先打个比方

ROS 像一栋办公楼里的广播系统：每个程序（节点）在自己的频道（话题）上广播或收听消息。TF 是贴在楼里的一张不断更新的“各部门相对位置图”，而且每张图都标了时间。

比喻只帮你建立直觉；下面用数字、公式和代码把它说准确。

一步步讲清楚

ROS 提供机器人程序之间的通信与工具。一个执行特定任务的程序组件叫节点；持续发送传感器数据的通道叫话题；通道中每一份结构化数据叫消息。话题名相同并不保证消息类型、时间和坐标定义正确。

典型数据流：激光驱动发布点云 → 估计器同时读 IMU → 输出位姿 → 建图和导航读取位姿。回调函数在数据到达时被调用，但到达顺序不一定等于采集时间顺序，缓存要按时间组织。QoS 是通信服务约定，例如可靠性和历史保留；不兼容时可能看见话题却收不到数据。

TF 管理不同坐标系随时间变化的变换。常见链是 map→odom→base_link→sensor。map 是全局参考；odom 通常连续但可漂移；base_link 附着机身；sensor 附着传感器。map→odom 可吸收全局校正，控制器因而可以使用连续的局部运动。名称语义应遵循项目约定与 REP-105。

消息中的 frame_id 声明数据在哪个坐标系，stamp 声明采集时刻。要把 t 时刻点云转换到地图，需要 t 时刻可用的 TF。用“最新变换”替代正确时间，在运动中会把墙抹成双层。每条 TF 的父子关系和发布者也应唯一明确。

录包（rosbag）把话题消息原样存下来，之后可以反复回放，做到“同一份数据、多次实验”。

ROS 1 和 ROS 2：两套命令，不能混用

ROS 有两代。本课程部署的 FAST-LIO2 官方 main 分支是 ROS 1（Noetic）；旧周教材的 ROS 示例多是 ROS 2（Jazzy）。两者的通信机制、构建工具和命令都不同，在 ROS 1 的终端里输入 ros2 命令只会报 command not found。AI 和网上教程经常把两者混在一起，看到命令先认清是哪一代。

FAST_LIO 上游另有 ROS2 分支，它是另一套工程。把 main 分支的 README 改几个命令，并不能变成 ROS 2 移植。

依次核对：消息类型 → 单位和坐标 → 时间单调与间隔 → TF 可用时间 → 通信兼容 → 才看算法输出。外参是传感器间刚体关系，时间偏差是另一个量；用错误外参去补偿时间差往往只在某种运动速度下看起来有效。

照着做：查看话题与 TF（ROS 1）

Python：可直接运行。先写下预测，再运行核对。

# ROS 1 终端命令（部署课使用 Noetic）；需先 source 环境，并有节点在运行或录包在回放
rostopic list
rostopic info /livox/imu
rostopic hz /livox/imu
rosrun tf tf_echo camera_init body
# ROS 2 对应写法：ros2 topic list / ros2 topic info / ros2 topic hz / ros2 run tf2_ros tf2_echo

list 列出当前所有话题名；info 显示消息类型、谁在发布、谁在订阅；hz 估计接收频率；tf_echo 打印两个坐标系之间的变换。/livox/imu、camera_init、body 是 FAST-LIO2 用 Avia 录包时的实际名字，你会在第 25 课亲眼看到。换成别的系统时，先用 list 查出实际名字再替换。输出取决于正在运行的系统，不能预先承诺某个频率。

核对解答与常见错因

检查点与 IMU 的时间戳、时间单位和去畸变；检查外参方向与旋转。用静止、直行、不同角速度录包作对照，不能仅凭症状确定唯一根因。

节点通过话题收发消息，消息要带坐标系和时间戳；TF 管理随时间变化的坐标变换；ROS 1 与 ROS 2 命令不能混用。
